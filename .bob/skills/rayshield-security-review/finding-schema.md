# RayShield Finding Schema

Reference for the canonical finding object produced by `scanProject()` in
`scanner/src/index.js`. Bob must work correctly with only the six required
fields. Optional fields provide richer context when available.

---

## Required fields (always present)

```json
{
  "id":          "3f7a1c2e-...",
  "rule":        "sql-injection",
  "severity":    "critical",
  "file":        "demo-app/src/db/queries.js",
  "line":        8,
  "description": "User-controlled input is directly incorporated into a SQL query."
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | UUID string | Generated by `crypto.randomUUID()` on every scan. **Never use this for verification.** It will not match between scans even for the same vulnerability. |
| `rule` | string | Stable identifier. Values: `sql-injection`, `xss-reflected`, `hardcoded-secret`. Use this for verification matching. |
| `severity` | string | `critical` or `high` (lowercase from scanner; frontend normalises to capitalised). |
| `file` | string | Relative path from the workspace root, e.g. `demo-app/src/db/queries.js`. Use this for verification matching. |
| `line` | integer | 1-based line number of the vulnerable expression. Use this for verification matching, with ±3 line tolerance to account for edits shifting line numbers. |
| `description` | string | Human-readable finding description from the scanner. |

---

## Optional contextual fields (present when scanner provides them)

These fields are not guaranteed. Bob must degrade gracefully when absent.

| Field | Type | Notes |
|---|---|---|
| `impact` | string | Pre-written impact description. Use if present; derive from code analysis if absent. |
| `action` | string | Pre-written remediation hint. Use if present; see `remediation-patterns.md` for the canonical approach. |
| `code` | string | The vulnerable code snippet as a string. Use if present; read from `finding.file` + `finding.line` if absent. |
| `confidence` | integer | 0-100. Scanner confidence in the finding. |
| `riskScore` | integer | Computed by `prioritize()` in the backend orchestration layer. |
| `context` | string | Repository context string from the Context Agent. |
| `source` | string | Agent that produced the finding, e.g. `code-agent`. |

---

## Verification matching rule

**Do NOT match by `id`.** Use this triple instead:

```
rule  === original finding.rule
file  === original finding.file
line  ~== original finding.line  (exact, or within ±3 lines)
```

A re-scan finding matches the original if all three conditions hold.
If no re-scan finding matches, the vulnerability is considered absent.

---

## .bobignore caveat

Files matching these patterns are blocked from Bob's context by `.bobignore`:
- `*config*` — this includes files like `demo-app/src/config.js`
- `*secret*`
- `*credentials*`
- `*.env`, `.env.*`

If `finding.file` matches a blocked pattern, Bob cannot read its contents
directly. In that case:
1. Note to the developer that the file is blocked by `.bobignore`
2. Ask the developer to paste the relevant code snippet
3. Proceed with the pasted content rather than skipping the review
